## 1. 结论摘要

这次采集比 2026-09-17 的首次测试明显更成功：连续 7 杆全部收到了球雷达结果和 GVP 相机 RESULT，相机没有阻塞雷达，也没有阻塞下一杆。

总体结论：

- 7/7 杆均保存了完整的球 PRC 点，球点数与设备期望值完全一致。
- 7/7 杆均收到了相机 RESULT，包含球、杆头和参考点的二维像素轨迹。
- 相机 RESULT 平均在触发后约 1.48 秒保存，雷达文件平均在约 2.79 秒保存，随后都正常回到 IDLE/重新准备状态。
- 所有球雷达点的 `dist_m` 仍然是 0，因此这次仍未从 PRC 中获得雷达逐点距离。
- 7 个相机结果中的 `cameraCalibration` 全部为 0，只有单目二维像素点，没有焦距、主点、畸变和相机位姿，所以相机目前也不能可靠补出绝对三维距离。
- Mevo 的 D4 `polyX/Y/Z` 仍可给出设备模型计算的三维球路，但它不是恢复出的原始雷达距离。
- 7 杆都有完整的 ED 杆头高层结果和 D9 速度曲线，但 7 个 `radar_club_raw.csv` 都只有表头。设备声明每杆有 50～80 个杆头 PRC 点，主动分页却全部超时，说明原始杆头分页存在系统性问题。
- 相机能够把击打时刻缩小到约一个或两个相机帧，典型分辨率约 5.53 ms；但 RESULT 没有直接提供“impact frame”，也没有雷达时钟到相机 Epoch 的精确映射，因此仍不能声称获得了绝对精确的撞击时刻。
- 相机检测总体可用，但并不干净：球轨迹较短，存在同一帧多个候选、静止球误检和少量明显跳点。应使用 `gvp_result_raw.json` 保留的全部候选做过滤，不宜直接把 CSV 每一行都当作真实飞行球点。

### 4.3 第 2 杆的 CSV 排序异常已经修正

第 2 杆的数据本身完整，但原始导出文件的行顺序曾经不是实际相对时间顺序。

设备计时器在本杆跟踪期间从接近 `262144` 回绕到 0。导出程序按 `time_tick` 数值直接排序，曾导致回绕后的后半段被排到文件开头：

```text
文件开头：index=10336, time_tick=73, n=0.27562
中间位置：index=23648, time_tick=13385, n=0.63061
随后跳到：index=0, time_tick=251881, n=0
文件末尾：index=10208, time_tick=262089, n=0.27221
```

分析时已将该文件按 `index` 从小到大重新排序。修正后的状态为：

- 第一行数据：`index=0, n=0, time_tick=251881`；
- 最后一行数据：`index=23648, n=0.63061, time_tick=13385`；
- `index` 和 `n` 现在都严格递增；
- 204 个数据点和每个点的所有字段均被原样保留，没有增删或重新计算。

修正后可以直接按文件行号、`index` 或 `n` 绘图。只有 `time_tick` 会在文件中从 `262089` 正常回绕到 `73`，所以它不再保持数值单调；计算相对飞行时间仍应使用 `n` 或 `index / 37500`。

这是导出排序问题，不是雷达漏点。其他 6 杆没有遇到计时器回绕，文件顺序原本就正常。当前只修正了这份已录制数据，导出程序的通用排序逻辑仍建议另行修改，避免以后遇到计时器回绕时再次出现同样情况。

## 5. 怎样理解相机数据

### 5.1 相机文件不是照片或视频

本次所谓“相机数据”是 GVP `SimpleObjectTracker` 输出的二维检测结果。目录中没有 JPG、原始帧或 MP4，因此只能分析物体在图像中的坐标，无法回看画面确认每一个检测框。

每杆包含：

| 文件 | 内容 |
|---|---|
| `camera_ball_raw.csv` | `trackId=0`，球的二维检测点 |
| `camera_club_raw.csv` | `trackId=1`，杆头的二维检测点 |
| `camera_reference_raw.csv` | `trackId>=2`，静止球/参考标记和内部辅助轨迹 |
| `gvp_result.json` | 解码后的完整 RESULT，包含所有 Track 和标定对象 |
| `gvp_result_raw.json` | GVP 发来的原始 JSON，最适合检查是否在导出时丢失候选点 |

### 5.2 相机 CSV 每个字段的含义

| 字段 | 含义和来源 |
|---|---|
| `shot_id` | 本项目添加的 Session 内杆号。 |
| `guid` | Mevo/GVP 的本杆关联 ID。 |
| `track_id` | GVP 对象类别：0 为球、1 为杆头，2～4 通常为参考标记；更高 ID 的精确含义尚未完全确认。 |
| `point_index` | 本项目写 CSV 时添加的数组下标，不是相机帧号。 |
| `frame_number` | GVP 的相机帧编号。 |
| `timestamp` | 该相机帧的 Unix Epoch 时间，单位秒，带小数。它来自 GVP 时间轴，不是雷达 `time_tick`。 |
| `u_px` | 图像水平方向像素坐标。 |
| `v_px` | 图像竖直方向像素坐标；从本批轨迹看，球升高时 v 通常减小，符合图像坐标向下为正的常见约定。 |
| `radius_px` | 跟踪器检测区域的等效半径，单位像素。它会受距离、运动模糊和分割形状影响，不一定等于清晰球轮廓半径。 |
| `circularity_factor` | GVP 的形状指标。球轨迹通常在 0～1 附近，越高一般越接近圆形；杆头和参考轨迹使用的数值尺度明显不同，不能跨对象直接比较。 |
| `shutter_time_ms` | 单帧曝光时间。本次所有保存点均为 1 ms。 |

同一个下标位置的 `frameNumber/timestamp/u/v/radius/circularityFactor/shutterTime` 属于同一次检测，不能把数组错位组合。

### 5.3 相机采样速度和覆盖范围

相邻相机帧的基础间隔约为 5.53 ms，对应约 181 fps。某些目标并非每一帧都检测到，所以相邻保存点可能跨 2～3 帧。

| 杆号 | CSV 球点 | CSV 杆头点 | 球帧范围 | 球轨迹覆盖时间 |
|---:|---:|---:|---|---:|
| 1 | 10 | 8 | 21～36 | 82.97 ms |
| 2 | 7 | 8 | 19～26 | 38.72 ms |
| 3 | 7 | 8 | 20～27 | 38.69 ms |
| 4 | 6 | 9 | 20～26 | 33.20 ms |
| 5 | 6 | 9 | 19～25 | 33.18 ms |
| 6 | 6 | 8 | 20～26 | 33.17 ms |
| 7 | 7 | 8 | 19～26 | 38.71 ms |

相机只观察了击球附近几十毫秒，而雷达观察球约 0.59～0.63 秒，两者用途不同：相机适合观察击球附近的二维运动，雷达更适合跟踪较长距离的飞行。

### 5.4 参考点的稳定性

`trackId=2` 给出了击球前静止球/主要参考点。七杆统计如下：

- `v` 平均约 322.63 px，标准差约 0.91 px；
- 半径平均约 12.19 px，标准差约 0.12 px；
- `u` 范围约 240.13～259.80 px，说明每杆放球的横向位置有一定变化；
- 参考质量指标为 90～100。

竖直位置和表观半径都很稳定，说明相机状态与雷达到球的大致纵向距离在七杆之间没有明显漂移。`u` 的变化更可能来自每次放球位置不同。

### 5.5 相机轨迹中的重复候选和误检

相机 RESULT 并非完全干净。

- 7 杆的 GVP 原始球 Track 一共有 59 个数组项；当前 CSV 按同一 `trackId + frameNumber + timestamp` 去重后只保留 49 个。
- 其中 10 个被去掉的项不是完全相同的数据，而是“同一帧的另一个候选位置”。
- 第 3 杆的杆头 Track 也有 1 个同帧候选被 CSV 去掉。
- 多杆球 Track 中出现靠近静止参考球位置的点，例如第 1 杆最后一点、第 2 杆最后一点、第 4/6 杆倒数附近的点。这些很可能是跟踪器重新识别到原地球影、背景目标或错误候选。
- 部分球点的 `circularity_factor` 只有约 0.15～0.25，说明轮廓较差或运动模糊明显。

例如第 1 杆 GVP 原始球 Track 在 frame 32 同时给出：

```text
(u=282.7, v=216.3, radius=6.8)   # 符合正在向上/远离的运动球
(u=258.2, v=334.9, radius=13.7)  # 接近静止球区域的另一候选
```

当前 CSV 去重规则只按帧号和时间戳判断重复，会丢掉第二候选，但它并没有记录“为什么选择第一个”。因此：

- 做严谨图像轨迹分析时应读取 `gvp_result_raw.json`；
- 需要结合前后帧连续性、参考球位置、半径变化和 D4 预期方向选择候选；
- 当前 `camera_ball_raw.csv` 适合快速查看，不应视为已经完成异常点清洗的最终轨迹。

## 6. 这次能否得到雷达缺失的距离信息

### 6.1 雷达 PRC 仍没有距离

7 杆共 1339 个去重球雷达点，`dist_m` 全部为 0。结论与首次测试相同：当前固件/PRC 版本没有在这个字段中提供可用逐点距离。

`--range-mm 2438` 只是雷达到初始球位的安装标定，不是设备自动测出的每个飞行点距离。

### 6.2 当前相机数据也不能可靠恢复绝对距离

7 个 `gvp_result.json` 的 `cameraCalibration` 全部是：

```json
{
  "cx": 0,
  "cy": 0,
  "fx": 0,
  "fy": 0,
  "width": 0,
  "height": 0,
  "position": [0, 0, 0],
  "rotation": [0, 0, 0],
  "distCoeffs": [0, 0, 0, 0, 0, 0, 0, 0]
}
```

缺少的关键参数包括：

- 焦距 `fx/fy`；
- 主点 `cx/cy`；
- 图像真实宽高和 ROI 关系；
- 镜头畸变参数；
- 相机相对于雷达的三维位置和旋转。

单目相机只凭 `(u,v)` 只能得到一条从相机出发的视线，不能确定该点在视线上的深度。

理论上，已知高尔夫球真实半径 `R` 和相机焦距 `f` 时，可以用近似关系：

```text
相机深度 Z ≈ f_px × R / radius_px
```

但本批数据不能可靠使用这个公式：

- `fx/fy=0`，没有像素焦距；
- `radius_px` 受运动模糊、目标分割和误检影响，部分飞行点半径反而大于静止球；
- 已知的 2438 mm 是雷达到球，不一定等于相机光心到球；
- 没有相机到雷达的外参，无法把相机深度转换到雷达坐标。

可以用静止球约 12.19 px 的半径和 2438 mm 做非常粗糙的比例估计，但动态球半径约为 6.8～17 px，会给出互相矛盾的距离，不能作为测量结果。

### 6.3 目前能够得到的三维位置

仍然只能可靠使用 Mevo D4 的：

```text
flight.polyX
flight.polyY
flight.polyZ
```

它们给出 Mevo 内部拟合并外推的三维模型位置。它可用于画轨迹、计算落点和任意模型时刻的位置，但应标记为“Mevo 模型结果”，不能标记为“相机补出的雷达实测距离”。

### 6.4 将来要用相机补距离，需要什么

至少需要：

1. 实际图像分辨率和 ROI；
2. 相机内参 `fx/fy/cx/cy` 和镜头畸变；
3. 相机相对雷达的平移与旋转外参；
4. 原始图像或视频，用于排除误检并验证 `radius_px`；
5. 相机时间与雷达 `time_tick/index` 的同步关系；
6. 使用已知球直径或多视角/其他几何约束求深度。

在这些条件满足前，本批相机点只能用于二维运动分析和击打时刻估计，不能补齐可靠的逐点距离。

## 7. 击打时刻能确定到什么程度

需要区分四种“时间”：

| 时间 | 含义 | 能否代表精确撞击 |
|---|---|---|
| `triggerEpoch` | 程序收到雷达击球触发消息的电脑时间 | 否；它比相机看到运动晚约 0.13～0.27 秒 |
| 相机 `timestamp` | 每个图像帧的 Epoch 时间 | 可以将撞击约束到若干帧，但 RESULT 没有直接标记 impact |
| 球 PRC 的 `n/index` | 相对第一个球雷达点的时间 | 能描述飞行点相对时间，但零点已经是球运动后 |
| ED/D9 的撞击前后字段 | Mevo 内部以撞击为零点的杆头拟合窗口和速度序列 | 有相对撞击概念，但当前没有映射到相机 Epoch 或球 PRC tick |

### 7.1 相机可以给出的近似撞击帧

一种可操作但仍是近似的方法是：

1. 用 `trackId=2` 确定击球前静止球中心；
2. 在 `trackId=1` 中找杆头中心最接近静止球的位置；
3. 在 `trackId=0` 中找第一个明显离开静止球的运动球点；
4. 将撞击时刻限制在这两个相机帧附近。

对第 2～7 杆，这两个事件通常相差 0～11.1 ms：

| 杆号 | 杆头最接近静止球的帧/时间 | 第一个运动球帧/时间 | 两者间隔 |
|---:|---|---|---:|
| 2 | frame 20 / `1789809301.622087` | frame 19 / `1789809301.616545` | 5.54 ms |

- 第 2～7 杆可以把相机内的撞击定位到约 1～2 帧；
- 基础帧周期约 5.53 ms；
- 考虑检测误差后，建议把实际不确定度理解为约 5～15 ms；
- 第 1 杆撞击帧不可靠。

### 7.2 为什么还不能与雷达点精确对齐

相机时间是 Unix Epoch，雷达 `time_tick` 是会回绕的设备内部计数器。本次文件没有保存两套时钟的同步映射。

另外，`triggerEpoch` 是雷达确认击球后程序记录的时间，明显晚于相机环形缓冲区中的击打画面，且每杆延迟不同。因此不能简单执行：

```text
雷达点 Epoch = triggerEpoch + n
```

这样会产生错误对齐。

若要精确同步，需要在采集时记录同一事件在雷达 tick 和 GVP timestamp 中的配对，或者取得带 `buf_ofs=0` 的原始杆头 PRC 点并建立两套时钟转换。

## 8. 杆头数据质量

### 8.1 高层杆头结果明显改善

与首次测试相比，这次 7 杆的 ED `club` 结果都包含丰富的非零字段：

- 撞击前杆速：21.21～27.95 m/s；
- 撞击后杆速：11.61～18.93 m/s；
- Attack Angle：-6.06°～+0.36°；
- 动态 Loft：15.56°～38.07°；
- 杆面角：-4.67°～+2.38°；
- 杆路方向：-5.11°～+5.06°；
- Smash：0.890～1.339；
- 撞击前拟合时间约 -40～-45 ms；
- 撞击后拟合时间约 +39～+78 ms。

D4 中的杆速、Attack Angle、动态 Loft、杆面角等与 ED `club` 基本一致，说明这些高层字段在消息之间关联正确。

### 8.2 原始杆头 PRC 仍全部缺失

每杆的 `club.numClubPrcPoints` 声明应有 50～80 点，但实际情况都是：

```text
clubPrcPageCount = 0
clubPrcPointCount = 0
clubPagesRequested = 1
clubPagesReceived = 0
clubTimedOut = true
```

因此所有 `radar_club_raw.csv` 都只有表头，所有 `radarComplete` 都是 `false`。

由于 7 杆完全重复同一种失败模式，这更像当前 0xEE 主动分页请求与固件响应方式不匹配，而不是偶发无线丢包。它不影响球 PRC 和 D4 保存，但目前无法：

- 查看每个杆头雷达点的时间、距离和速度；
- 使用 `buf_ofs=0` 直接定位撞击点；
- 独立复算杆头轨迹、Attack Angle 或杆面参数；
- 验证 ED 杆头多项式的逐点残差。

### 8.3 D9 速度曲线可以使用，但要识别零填充

每杆都有 `speedProfile`。撞击前的非零速度整体随挥杆加速，并且末端/最大值与 ED `preClubSpeedMps` 接近，说明撞击前速度曲线具有实际信息。

但数组包含大量 0：

- 第 1 杆前后两段都完整，中间有 23 个零填充；
- 第 2～7 杆的撞击后区域多数只保存了 0～7 个非零值，其余位置为零；
- 个别撞击前区域也夹有单个 0。

这些 0 不应解释为杆头速度突然降为 0 m/s，更像固定长度缓冲区的空槽或未检测样本。分析时应结合 `numPre`、`numPost`、非零连续段和 ED 的 `pre/postClubSpeedMps`，不能直接对整个数组求平均。

### 8.4 `clubToBallTimeMs`

七杆的值为：

```text
17.06, 5.97, 5.97, 9.38, 8.53, 8.53, 6.82 ms
```

这是 Mevo ED 消息中的内部杆头事件到球事件时间量。它说明设备内部确实建立了撞击附近的相对时间关系，但当前缺少原始杆头 PRC 和官方零点定义，不能直接把它加到相机 timestamp 或雷达 `n` 上。

## 9. 旋转结果质量

7 杆都收到了 EF 旋转结果，D4 倒旋与 `pmSpinFinalRpm` 很接近。最终倒旋 2502～5189 rpm，与不同动态 Loft、起飞角和击球强度的变化整体相容。

注意两点：

## 11. 后续最值得改进的事项

按优先级建议：

1. 修复/研究 0xEE 杆头 PRC 请求，确认固件是否要求不同请求长度、索引步长或时机。
2. 修正球 CSV 排序：优先按 `index/n` 排序，并正确处理 `time_tick` 回绕。
3. 相机 CSV 不要仅按 `(trackId, frameNumber, timestamp)` 去重；应保留同帧候选并增加 `candidate_index`，避免静默丢失不同位置的检测。
4. 保存相机真实内参、分辨率、ROI 和相机到雷达外参；否则不能从像素恢复绝对距离。
5. 若设备允许，保存原始帧或短视频，以便人工验证球/杆头误检和撞击帧。
6. 在采集时增加雷达 tick 与 GVP timestamp 的同步事件，才能把每个雷达点精确对应到相机帧。
7. 解码 D9 时识别固定缓冲区中的零填充，分别导出有效的撞击前和撞击后速度样本。

在当前状态下，这批数据已经适合分析最终球路、击球参数趋势和二维击打过程；但还不适合宣称获得了原始三维测距、精确撞击时间或完整的原始杆头雷达轨迹。
