## 4. 为什么判断球数据是合理的

### 4.1 点数和分页完整

第一杆：

- 设备预期球点数：110
- 去重后实际球点数：110
- 请求/收到分页：28/28
- `ballComplete=true`
- `ballTimedOut=false`

第二杆：

- 设备预期球点数：105
- 去重后实际球点数：105
- 请求/收到分页：27/27
- `ballComplete=true`
- `ballTimedOut=false`

因此第二杆的 `radarComplete=false` 不是球分页问题，而是杆头 PRC 分页问题。

### 4.2 时间和索引连续

两份 CSV 中：

- `time_tick` 全程严格递增；
- `index` 全程严格递增；
- 每一个点都满足 `index = time_tick - 本杆第一个 time_tick`；
- `n` 近似满足 `n = index / 37500`，即它在这批数据中实际表现为“从本杆跟踪起点开始经过的秒数”；
- 最后一个点的 `n` 分别为 `0.62976` 和 `0.61610`，与 D4 的跟踪时长一致。

采样不是固定频率。常见相邻间隔是约 1.71、3.41、6.83 和 13.65 ms，最大一次约 23.9 ms。这种 64/128/256/512 tick 的分级间隔符合设备对跟踪点进行选择或降采样的表现，不像随机卡顿造成的数据破损。

### 4.3 原始角度和径向速度变化连续

| 原始量 | 第一杆 | 第二杆 |
|---|---:|---:|
| `az_deg` 范围 | -11.68° ～ -1.99° | -1.47° ～ +6.75° |
| `el_deg` 范围 | -0.89° ～ 18.02° | -0.97° ～ 11.58° |
| 径向速度范围 | 12.21 ～ 14.25 m/s | 16.00 ～ 17.72 m/s |
| SNR 原始值范围 | 12 ～ 426 | 14 ～ 457 |
| 最大单步速度变化 | 0.14 m/s | 0.34 m/s |

角度随球离开雷达逐步变化，径向速度总体平滑下降；SNR 和各天线峰值随时间明显减弱，也符合球逐渐远离雷达后回波变弱的预期。

这里的原始 `az_deg`、`el_deg` 是雷达观察球所在方向的视线角，不是球速向量的起飞角。因此它们不应直接等同于 `flight.launchAzimuthDeg` 和 `flight.launchElevationDeg`。同样，`radial_velocity_mps` 只是在雷达视线方向上的速度投影，通常会小于最终给出的真实起飞球速。

### 4.4 最终轨迹内部高度一致

D4 `flight` 内的轨迹多项式为：

```text
x(t) = polyX[0] + polyX[1]t + ... + polyX[4]t^4
y(t) = polyY[0] + polyY[1]t + ... + polyY[4]t^4
z(t) = polyZ[0] + polyZ[1]t + ... + polyZ[4]t^4
```

其中 `t` 的单位为秒，有效范围是 `0 <= t <= flightTimeSeconds`。

对两杆进行独立复算后：

- 多项式在 `t=0` 的一阶导数得到的起飞速度分别为 15.448 和 18.606 m/s，与报告值 15.453 和 18.609 m/s 只差约 0.005 和 0.003 m/s；
- 复算出的起飞水平角、仰角与报告值误差约 0.01°；
- 多项式飞到落地时刻后，与报告落点的三维误差分别只有约 6.4 mm 和 7.8 mm；
- `sqrt(落点前进距离² + 落点侧向距离²)` 分别为 21.002 m 和 24.430 m，与 Carry 21.003 m 和 24.431 m 只差约 1 mm；
- 多项式复算的最高点分别约为 3.281 m 和 2.436 m，与报告值差异极小。

这组一致性是判断数据解码正确、单位正确的强证据。

### 4.5 D4 和 E8 结果互相吻合

`flightV1`（E8）是较早的阶段性结果，`flight`（D4）是后续完整结果。

- 第一杆两者的球速、Carry、最高点、飞行时间和倒旋完全一致。
- 第二杆球速完全一致，Carry 相差 0.086 m，最高点相差 0.008 m，飞行时间相差 0.006 s，倒旋相差 271 rpm。这符合后续算法继续修正结果的特征。

实际使用时建议以 D4 `flight` 为准。

## 5. 每类字段应该怎样理解

### 5.1 `summary.json`：优先看的结果文件

日常分析一杆球，首先看这些字段：

| 字段 | 含义 |
|---|---|
| `flight.launchSpeedMps` | 最终起飞球速，不是单个雷达点的径向速度 |
| `flight.launchAzimuthDeg` | 最终水平起飞角 |
| `flight.launchElevationDeg` | 最终垂直起飞角/VLA |
| `flight.carryDistanceM` | 空中 Carry，不含落地滚动 |
| `flight.maximumHeightM` | 轨迹最高点 |
| `flight.flightTimeSeconds` | 模型推算到落地的总飞行时间 |
| `flight.trackTimeSeconds` | 雷达真正观察到球的时间，不等于完整飞行时间 |
| `flight.landingPositionM` | `[前进, 竖直, 侧向]` 落点坐标 |
| `flight.landingVelocityMps` | 落地瞬间的三轴速度；Y 为负表示正在下落 |
| `flight.backspinRpm` | 最终采用的倒旋 |
| `flight.polyX/Y/Z` | 设备拟合并外推到落地的三维轨迹多项式 |

雷达只实际跟踪了约 0.62 秒，但报告了约 1.55–1.73 秒的完整飞行时间。这不是矛盾：前一段来自实际雷达跟踪，后一段由设备根据已测轨迹、速度和旋转拟合外推到落地。

### 5.2 `radar_ball_raw.csv`：球的原始离散测量

| 字段 | 在这批数据中的正确理解 |
|---|---|
| `shot_id`, `guid` | 本地杆号和设备 GUID，用于关联同一杆的不同消息 |
| `page_sequence` | PRC 分页序号，每页通常含 4 点；不是时间 |
| `index` | 相对本杆起点的 tick 索引；本批数据与 `time_tick` 的差值完全对应 |
| `buf_idx` | 设备内部缓冲区索引，不建议作为物理量使用 |
| `flags` | 原始状态位；两杆所有点均为 9，未发现中途状态变化 |
| `time_tick` | 设备时间计数；当前程序按约 26.7 微秒/tick 转为 `time_seconds` |
| `time_seconds` | `time_tick` 换算后的设备计数时间，不是 Windows 时间，也不是本杆从 0 开始的时间 |
| `n` | 虽然当前代码注释仍称其为折射率因子，但本批所有数据都表明它是相对时间量，约等于 `index / 37500` 秒 |
| `az_deg`, `el_deg` | 雷达到球的视线方位角和仰角，不是最终起飞方向 |
| `radial_velocity_mps` | 球沿雷达视线方向的速度分量，不是三维总球速 |
| `dist_m` | 本批数据全部为 0，当前不可用 |
| `snr` | 协议中的原始信噪/质量量；单位尚未确认，不应直接当作 dB |
| `peak` | 设备原始峰值相关索引/量，数值几乎固定；不要单独把它当回波强度 |
| `az1/2/3`, `el1/2` | 不同天线通道各自估计的角度，可用于检查通道一致性 |
| `pk0..pk5` | 六路天线峰值量；两杆都随距离增加而整体下降 |
| `sync_idx`, `sync_buf` | 内部同步字段，本批固定为 0 和 -1，不用于常规球路分析 |

第一杆不同天线间的最大方位角差约 1.29°、最大仰角差约 1.28°；第二杆分别约 0.56° 和 0.55°。没有看到某一路天线完全脱离其他通道的异常。

### 5.3 `radar_club_raw.csv`：本次没有取得原始杆头点

两个文件都只有表头，没有数据行，但原因不同：

- 第一杆的 `ClubResult.numClubPrcPoints=0`，设备本身没有声明杆头原始点，所以没有请求杆头分页，整体雷达仍可判定完整。
- 第二杆设备声明存在 17 个杆头点，也给出了 26.05 m/s 的高层杆头速度和 0.714 的 Smash Factor，但程序请求杆头 PRC 页时超时，实际原始点为 0。

因此第二杆可以使用高层 `club` 结果作参考，但不能做逐点杆头轨迹分析。0.714 的 Smash Factor 对正常扎实击球偏低，但对短杆小挥幅、非甜点击球或杆头测量不稳定可能出现；仅凭这一杆不能判断设备故障。

- `session.json`：本次运行参数与完成杆数。
- `session.log`：连接、触发、GVP 断线和文件保存时间线。

两杆日志都出现：


所以没有相机数据是有明确日志依据的，不是文件被漏放到其他目录。

## 6. 取出一行数据，逐项解释来源和含义

用户问题中的“取出一列数据”，这里按“从 CSV 中取出一行完整记录”理解。CSV 中一行代表一个时间点上的球雷达 PRC 跟踪点；一列则只会包含同一种字段，无法同时解释所有项目。

### 6.1 先区分四种数据来源

`radar_ball_raw.csv` 这个名字中的“raw”是指**协议层的 PRC 原始跟踪点**，并不是雷达射频 ADC/IQ 原始采样。Mevo 已经先在设备内部用 DSP 对雷达回波做了目标检测、测速、测角和峰值提取，本项目再把设备发来的二进制字段解码成 CSV。

本节用以下四类来源标记每个字段：

| 来源分类 | 准确定义 | 例子 |
|---|---|---|
| A. 本项目元数据 | 由导出程序为了组织文件和关联击球而添加，不来自这一条雷达 PRC 记录 | `shot_id` |
| B. Mevo 协议/设备元数据 | Mevo 提供的击球或分页标识，但不是球的物理测量量 | `guid`、`page_sequence` |
| C. Mevo 雷达/DSP 输出 | 来源是设备的 PRC 记录；角度、速度等已经由 Mevo DSP 从雷达回波中估计，并非本项目算法计算 | `az_deg`、`el_deg`、`radial_velocity_mps`、`snr` |
| D. 本项目换算值 | 本项目基于 Mevo 原始整数做单位换算或派生计算 | `time_seconds`；其他带物理单位的字段也经过解码比例换算 |

需要特别注意：一个字段可以同时具有“底层来自 C、显示形式经过 D 换算”两层来源。例如 `az_deg=4.14` 的角度估计来自 Mevo，项目只负责把线上的整数 `414` 除以 100，项目没有重新计算球的方向。

### 6.3 28 个字段逐项解释

| 序号 | 字段和值 | 来源 | 详细解释 |
|---:|---|---|---|
| 1 | `shot_id = 1` | A. 本项目元数据 | 当前 Session 内的本地杆号。导出程序每次启动会新建 Session，并从 1 开始编号。它不是 Mevo 设备历史总杆数；设备内部总杆数在 `summary.json` 的 `flight.shotCounter` 中，本杆为 4。 |
| 2 | `guid = {6aab477a-...-0001}` | B. Mevo 击球标识 | Mevo 为本次触发提供的全局关联标识。球 PRC、最终飞行结果和相机触发都用它判断是否属于同一杆。本项目原样写入，未计算或修改。 |
| 3 | `page_sequence = 52` | B. Mevo 分页元数据 | 这条点所在 PRC 页的序号/起始位置。当前协议每页通常最多返回 4 个点，所以页序号通常按 0、4、8……变化。它不是第 52 秒，也不是第 52 个采样点。 |
| 4 | `index = 6208` | C. Mevo PRC 原始字段 | 相对本杆第一个跟踪点的时间 tick 索引，不是普通的行号。本批数据中它严格满足 `153129 - 146921 = 6208`，即当前 `time_tick` 减去本杆首点 `time_tick`。 |
| 5 | `buf_idx = 35` | C. Mevo PRC 原始字段 | Mevo 内部雷达/跟踪缓冲区索引。它可能循环或跳变，不应当作时间、距离或点序号。本项目主要保留它用于原始记录检查及去重。 |
| 6 | `flags = 9` | C. Mevo PRC 原始字段 | PRC 点的状态位，十进制 9 等于二进制 `0b00001001`。目前尚未确认各 bit 的官方含义，因此不能自行解释为“有效”“锁定”等具体状态。两杆所有球点都是 9，至少说明跟踪过程中该状态没有突变。 |
| 7 | `time_tick = 153129` | C. Mevo PRC 原始字段 | Mevo 的设备时间计数器。每 tick 约 26.7 微秒。它的零点不是击球时刻，也不是 Windows 系统时间，所以这个整数主要用于排序和计算点间时间差。 |
| 8 | `time_seconds = 4.088544300` | D. 本项目计算 | 项目执行 `153129 × 26.7 × 10⁻⁶ = 4.0885443 s` 得到。它只是把设备计数器换算成秒，仍然不是本杆从 0 开始的相对时间。转换代码位于导出程序，不是 Mevo 直接发送的浮点数。 |

### 6.4 这一行能告诉我们什么，不能告诉我们什么

能够直接判断：

- 该点位于本杆跟踪开始后约 0.16554 秒；
- 球仍被雷达稳定跟踪，多个角度通道高度一致；
- 球的视线方向约为方位 `+4.14°`、仰角 `+10.38°`；

不能只用这一行得到：

- 球此时的三维总速度，因为只有径向速度；
- Carry、最高点或落点，因为这些需要整段跟踪及 Mevo 内部飞行模型；
- 倒旋、侧旋和杆头数据，因为它们来自其他 Mevo 消息，不在球 PRC 单点中；
- 相机坐标，因为本次 GVP 没有返回相机结果。

### 6.5 原始点与最终结果的计算边界

从数据流角度，可以这样理解：

```text
雷达回波
  -> Mevo DSP 检测并跟踪目标
  -> Mevo 生成 PRC 点（时间、视线角、径向速度、信号量等）
  -> 本项目解码比例、去重并写入 radar_ball_raw.csv

整段 PRC 跟踪 + Mevo 的内部弹道/旋转算法
  -> Mevo 生成 D4 flight（总球速、起飞角、Carry、轨迹多项式等）
  -> 本项目仅解码并写入 summary.json
```

因此，本项目当前没有根据 CSV 自己重新拟合 Carry，也没有把原始角度和径向速度自行融合成三维轨迹。`summary.json` 中的 D4 球路结果来自 Mevo 内部计算；本项目做的是协议解码、单位缩放、记录关联、去重和文件输出。

### 7.8 `spin`：Mevo EF 旋转结果

这一对象来自 Mevo EF `SpinResult`。Mevo 同时保留多个内部旋转算法或候选结果，再选择最终值。

1. 先看 `warnings`、`radarComplete` 和 `pagination`，判断缺失范围。
2. 看 `flight` 获取最终球速、角度、Carry、落点和轨迹。
3. 用 `flight.trackTimeSeconds` 与 `ballPrcPointCount` 检查原始跟踪覆盖。
4. 看 `spin.pmSpinFinalRpm` 和 `flight.backspinRpm` 是否一致。

## 8. 几个容易误判的问题

### 8.1 `dist_m=0` 是否表示雷达测距失败

不能这样解释。

两杆所有原始点的 `dist_m` 都为 0，但角度、径向速度、跟踪时间和最终飞行结果都连续且自洽。更合理的结论是：当前固件/PRC 数据版本没有填充这个字段，或者它在该模式下不是可用的绝对距离字段。

由于导出目录没有保存原始二进制包，仅凭 CSV 不能进一步区分“固件未填充”和“协议字段含义仍需修订”。现阶段应把 `dist_m` 标记为不可用，而不是用 0 参与计算。

命令行的 `--range-mm 2438` 是雷达到击球位置的安装标定值，与飞行中每个点的动态距离不是同一个概念。即使 PRC 的 `dist_m` 没有输出，设备仍可使用已知安装距离、角度、径向速度和内部算法求出最终球路。

### 8.2 为什么有 112/108 个 duplicate 点

这不是 CSV 里出现重复行。

程序既接收设备主动发送的 PRC 页，又启用了主动分页补取，因此同一批点可能被收到两次。第一杆共缓存 56 页、第二杆共缓存 54 页，而主动分页实际分别是 28 页和 27 页，正好体现了这种重叠。程序按 `(index, time, buf_idx)` 去重后再写 CSV，最终点数与设备预期完全一致。

### 8.3 `flightV1.trackedTimeSeconds` 为什么是 11.691 和 7.082

这两个值与原始点覆盖的 0.630/0.616 秒明显不符，也与 D4 `trackTimeSeconds` 不符。因此，在当前协议理解下，不应把 E8 的这个字段当作真实跟踪时长。真实跟踪时长应优先采用：

1. D4 `flight.trackTimeSeconds`；
2. 或原始 CSV 最后一个点的相对时间 `n`。

### 8.4 `sidespinRpm=0` 是否表示球绝对没有侧旋

不能据此下结论。两杆都有明显的水平起飞角和侧向落点，但设备在此次结果中没有给出侧旋或旋转轴角。这里的 0 更适合解释为“未输出/未解算出可用侧旋”，而不是物理上严格为零。

## 9. 怎样用这些数据

### 9.1 只想知道这一杆打得怎样

直接读取 `summary.json` 的 D4 `flight`：球速、起飞角、Carry、最高点、落点、飞行时间和倒旋已经足够。

### 9.2 想画完整三维球路

使用 `flight.polyX`、`polyY`、`polyZ`，在 `0` 到 `flightTimeSeconds` 之间均匀取样。不要使用本批 CSV 的 `dist_m` 画轨迹。

### 9.3 想检查雷达原始跟踪质量

建议依次检查：

1. `pagination.ballComplete` 是否为 `true`；
2. `ballPrcPointCount` 是否达到 `expectedBallPrcPointCount`；
3. `time_tick` 和 `index` 是否单调递增；
4. 最后一个 `n` 是否接近 `flight.trackTimeSeconds`；
5. `az_deg`、`el_deg`、`radial_velocity_mps` 是否连续；
6. 后段 SNR/天线峰值是否仍明显大于零。

本次两杆都通过了以上球数据检查。

## 10. 最终评价

这批首次实测数据证明：当前导出程序已经能够稳定取得 Mevo+ 的球雷达原始点和最终飞行结果，球数据本身具有很强的内部一致性，足以用于球路结果读取、质量检查和按 D4 多项式绘制三维轨迹。

当前主要缺口不是球雷达数据质量，而是：

1. GVP/相机连接在两杆触发后都断开，没有相机数据；
2. 第二杆的杆头 PRC 主动分页超时，只有高层杆头结果，没有原始杆头点；
3. `dist_m` 在当前固件数据中全部为 0，不能用于逐点三维定位；
4. `n` 和 `flightV1.trackedTimeSeconds` 的现有代码注释/命名与实测语义不完全相符，后续协议文档应按实测结果修正。

在不考虑相机和原始杆头点的前提下，两杆的球雷达结果可判定为**合理、可用**。
